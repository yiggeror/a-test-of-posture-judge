# 部署到小程序:约束与选型

面向「做成小程序、要有一定准确性、非医用级」这个目标。
下面的数字都是本仓库实测的,不是估计。

---

## 一个必须先知道的绑定关系

**本项目所有的阈值、不确定度和噪声模型,都绑定在 BlazePose 的 33 点拓扑上。**

- 每项 ± 是按「该指标两个端点各自的实测噪声 ÷ 测量跨度」算出来的
- `reports/landmark_noise.json` 是逐关键点的,例如耳 0.0068、肩 0.0207
- 阈值分位数来自这些点位在参考集上的分布

**换一个姿态模型,这些全部作废。** 不同模型的关键点定义、耳朵位置、髋关节中心
的约定都不一样,噪声特性更不一样。

这一条现在是实测过的,不只是推断:`scripts/compare_models.py` 把同一家族、同一
拓扑、体积小三分之二的 `pose_landmarker_full` 和 heavy 放在 73 张照片上对比
(`reports/model_swap.json`)。头部前移读数在 58% 的照片上两者之差超过读数自身
的 1σ,耳肩角在 68% 上超过,还有 3 张照片连正/侧面的判断都不同。连同家族的小
模型都是另一台仪器。如果端侧改用小程序自带的人体关键点能力或
别的模型,必须把 `repeatability.py` 和 `reference_distribution.py` 在新模型上
重跑一遍,否则 ± 和阈值就是从另一个仪器上抄来的数字。

这一条决定了下面两条路的代价差异。

## 实测数据

| 项目 | 数值 |
|---|---|
| `pose_landmarker_heavy.task` | 30.7 MB |
| `pose_landmarker_full.task` | 9.4 MB |
| `efficientdet_lite0.tflite`(独立人体检测守卫) | 13.8 MB |
| 姿态检测单张耗时(容器 CPU) | 69 ms |
| 完整评估,含深度守卫 | 777 ms |
| 完整评估,跳过深度守卫 | 58 ms |

777ms 里的大头是深度守卫要**跑三次模型**:姿态 + 独立人体检测 + 稳定性检查
的第二次姿态。这三次不是浪费——独立检测是抓「手掌照被贴上骨架」那一类的唯一
手段,稳定性检查是抓「头发盖住耳朵但 visibility 报 1.000」的唯一手段。
砍掉它们会让假阳性泄漏率从 6% 回升。

---

## 两条路

### A. 后端 API

小程序上传照片 → 服务端跑 MediaPipe → 返回 JSON。`api.py` 已经实现。

**优点**
- 模型不受包体限制,可以用 heavy(精度最好的那个)
- 所有守卫都能跑,假阳性泄漏保持在 6%
- 阈值/噪声模型直接复用,不需要重新标定
- 逻辑只有一份,以后改阈值不用发版

**代价**
- 全身照要上传。这是**隐私敏感数据**,比一般图片更敏感。
- 服务器成本和延迟

`api.py` 的写法已经按「不落盘、不记录图片字节」来做了,但这只是代码层面的
事实,**留存策略是产品决定**,上线前要明确回答:传输是否加密、处理完是否立即
丢弃、是否需要用户明示同意。这不是我能替你定的。

### B. 端侧推理 —— 浏览器里已经实现

`web/` 就是这条路:MediaPipe 的 JS 版在浏览器里跑 heavy 模型,照片不离开设备。

- **模型不进包体,运行时下载。** wasm 11.8 MB + heavy 模型 30.7 MB(拆成 3 片,
  每片 ≤14 MB),页面打开就在后台下载,之后走浏览器缓存。
- **没有换模型,所以不用重新标定。** 同一个 heavy 模型,JS 与 Python 在同一张图上
  的关键点差异中位数是体长的 0.003%,最大 0.04%。
- **整条判定链路逐项核对过。** `scripts/build_web.py` 在 116 张照片上比对 Python
  与 `web/posture.js` 的守卫、读数、档位和用户看到的报告,0 差异,否则构建失败。
- **少了一道守卫**:独立人体检测(EfficientDet,13.8 MB)没有放进浏览器。它拦的
  是「手掌特写被贴上骨架」这类输入,主动上传自己全身照的用户很少会遇到。
  关键点稳定性守卫在浏览器里有。

**小程序怎么接**(以下是选项,具体限制以微信当前文档为准,我没有在微信环境里验证):

1. **web-view 直接嵌这个网页。** 改动最小,功能完全一致。前提是网页部署在小程序
   配置过的业务域名下。
2. **小程序原生页面 + 后端 API(路线 A)。** 界面用小程序组件写,直接渲染 API 返回
   的 `report` 字段——和网页是同一份文案、同一套映射。
3. **小程序原生 + 端侧推理。** 需要小程序运行时能跑这个 wasm 并在运行时下载模型;
   逻辑层直接复用 `web/posture.js`。三条里工作量最大、我验证得最少的一条。

**优点**:照片不出设备,隐私问题消失;不需要服务器。
**代价**:首次 42 MB 下载;手机 CPU 上单次推理比服务器慢(每张照片跑两次:一次检测,
一次稳定性检查)。

---

## 建议路径

1. **先用 web-view 嵌网页,或走 API。** 两者都已可用、结论一致。网页版隐私更好;
   API 版可以统计真实用户照片的分布,用来重算阈值。
2. **前端做拍摄引导,而不是事后拒绝。** 网页首页的三条拍摄提示和被拒时的具体
   重拍提示就是这个用途。抓拍的侧面照 31 张里只有 3 张能出结论(多数是走路中、
   膝盖弯着),按提示拍的工作室照片全部能出。
3. **不要为了省下载量换小模型。** 那需要把 `repeatability.py` 和
   `reference_distribution.py` 在新模型上重跑一遍,见开头的绑定关系。

## 前端该怎么用这个 API

**只想给用户看结论,就只渲染 `report` 字段。** 它是 `posture/report.py` 的输出:
问题(名称、程度、一句话说明、原因、三个改善动作)、正常项、这次没检查的项及原因、
需要重拍时的具体提示、拍摄小建议、免责声明。网页用的是同一个函数的 JS 移植。

下面这些是给调试和审计用的原始数据:

- `metrics[]` — 读数。**每一项都带 `threshold_provenance`**,值可能是
  `population-percentile`(实测分位数)或 `guess`(手定)。
  当前 6 项判定指标里 5 项是实测、1 项(躯干前后倾)是手定。
  **界面上把手定的那项和实测的混在一起展示,就是在把猜测当测量卖。**
- `blocked_by[]` / `warnings[]` — 结构化的拍摄问题。这些应该变成
  **拍摄前的引导**,不是拍完之后的报错。用户自拍时最常见的是脚出画、
  斜侧角度、手臂没垂放,这三个在取景阶段就能提示。
- `unavailable[]` — 因为某个关键点在画面外而停用的指标。这不是失败:
  脚出画只会停用「躯干前后倾」,头肩类指标照常出。界面应该显示
  「这次少测了哪项、为什么」,而不是让用户以为分析失败了。

还有两条硬性的:

- `band` 在工具没有把握时是 `null`。**不要自己补一个。** 读数的误差棒骑在
  阈值上时,工具故意不给档位,这是本项目最核心的设计。
- `report.disclaimer` 必须展示(一句话,放在页面角落即可)。措辞用「参考」「倾向」,
  不用「诊断」。
- 手机照片带 EXIF 方向标记。API 现在会按标记转正(`load_rgb`);之前不会,竖拍的
  照片会被当成横躺的人。

## 准确性现在是什么水平

对照「有一定准确性、非医用级」这个标准:

| | |
|---|---|
| 旋转追踪(已知真值) | 九项指标全部在理论值 ±0.05 以内 |
| 对真实姿态变化的响应 | 斜率 1.007 / 0.984,**不会系统性低估** |
| 正面指标严重误差率 | 1–3% |
| 侧面长跨度指标 | 抓拍 5%,摆拍 0% |
| 假阳性泄漏 | 6%(上一轮 29%) |
| 阈值 | 6 项里 5 项实测分位数 |

**够用。** 但两条边界要在产品里说清楚:

1. **没有临床效度,而且这个项目不会有。** 阈值是常模参照——「你的读数在一堆
   照片里排第几」,不是「你有没有问题」。参考人群是未筛查的普通照片。
   **异常 ≠ 不健康。**
2. **侧面那两个实测阈值基于 n=35**,过了 n≥20 的最低门槛但不是稳定估计。
   标为 provisional。拿到真实用户照片后可以用同样的脚本重算。
